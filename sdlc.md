# How to use SDLC

## Introduction

The Software Development Life Cycle (SDLC) is a structured process that teams use to plan, build, test, release, and maintain software. Each phase has a clear purpose and produces specific outputs that feed into the next phase.

### Why technical writers need to understand SDLC

Documentation depends on the product, and the product changes at every phase of the SDLC. When you understand the phases, you can:

* Know when information becomes available and who owns it.
* Join conversations early, when your questions can still influence the product.
* Plan your writing, reviews, and publishing around release milestones.
* Speak the same language as developers, testers, and product managers.

### Who this article is for

This article is for technical writers who are new to software projects or who want a clearer view of how software gets made. It's also useful for content developers, documentation managers, and anyone who works with engineering teams. You don't need a programming background to follow along.

## Phase 1: Planning

### Purpose

Planning defines why the project exists and what it needs to succeed. The team decides on the project goals, scope, schedule, budget, and resources.

### Key activities

* Define the business goals and the problem the software solves.
* Estimate cost, time, and staffing.
* Identify risks and plan how to reduce them.
* Decide which development approach the team will use.

### Output

* Project plan
* Feasibility study
* Resource and schedule estimates

## Phase 2: Requirements analysis

### Purpose

Requirements analysis describes what the software must do. The team collects needs from customers, stakeholders, and subject matter experts (SMEs), and then turns those needs into clear, testable statements.

### Key activities

* Interview stakeholders and review customer feedback.
* Separate functional requirements (what the software does) from nonfunctional requirements (how well it performs, such as speed and security).
* Resolve conflicts and remove ambiguity.
* Get approval from stakeholders.

### Output

* Software requirements specification (SRS)
* User stories or use cases
* Acceptance criteria

## Phase 3: Design

### Purpose

Design describes how the software will meet the requirements. Architects and developers decide on the structure of the system, the technologies to use, and how the parts fit together.

### Key activities

* Create the high-level design, which covers the overall architecture and major components.
* Create the low-level design, which covers modules, classes, data models, and interfaces.
* Design the user interface and user experience.
* Define how the system connects to other systems, for example through APIs.

### Output

* Architecture diagrams
* Design documents
* Database schemas
* UI mockups and prototypes

## Phase 4: Development

### Purpose

Development turns the design into working software. Developers write, review, and combine code according to the design and the coding standards the team agreed on.

### Key activities

* Write code for each feature or module.
* Review code with peers.
* Manage code changes in a version control system, such as Git.
* Build and integrate the modules regularly.

### Output

* Source code
* Working builds
* Code comments and developer notes

## Phase 5: Testing

### Purpose

Testing verifies that the software meets the requirements and works as expected. Testers find defects so that the team can fix them before users see them.

### Key activities

* Run unit tests, integration tests, system tests, and user acceptance tests.
* Log defects and track them until they're resolved.
* Retest fixes to confirm that they work and don't break anything else.
* Check performance, security, and usability.

### Output

* Test plans and test cases
* Test reports
* Defect logs
* Approved release candidate

## Phase 6: Deployment

### Purpose

Deployment releases the tested software to users. The team moves the software into the production environment and makes it available.

### Key activities

* Prepare the production environment.
* Install or publish the software, either in stages or all at once.
* Monitor the release for problems.
* Communicate the release to customers and support teams.

### Output

* Released software
* Release notes
* Deployment and rollback plans

## Phase 7: Maintenance

### Purpose

Maintenance keeps the software working and useful after release. The team fixes issues, responds to user feedback, and adds improvements over time.

### Key activities

* Fix bugs reported by users.
* Apply security patches and performance updates.
* Add new features or change existing ones.
* Retire features that are no longer needed.

### Output

* Patches and updates
* Updated release notes
* Support and incident records

## Conclusion

SDLC gives you a clear map of how a product moves from an idea to a supported release. When you know what happens in each phase, you can anticipate what information you need and who can provide it. You can also plan your documentation work around real milestones instead of last-minute requests. Use this article as a reference when you join a new project, and you'll ask better questions, collaborate more effectively, and deliver more accurate documentation.
